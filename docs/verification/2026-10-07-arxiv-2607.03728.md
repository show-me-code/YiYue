## 这篇论文暴露并修掉的问题（4 个）

1. **源码本身在本工具链下编译不过**（`Option clash for package xcolor`）。
   作者的 `00README.json` 指定 TeX Live 2025 + pdflatex；Tectonic 内置的是 LaTeX
   2021，那里的 eso-pic 会**无选项**加载 xcolor，之后 `iclr_palette.tex` 又写
   `\usepackage[table,dvipsnames]{xcolor}` → 直接报错。实测**不加任何处理**的原始
   源码同样是这个错，所以整条 arXiv 路线此前一直静默回退到 PDF 原位排版。
   修复：`repair_from_log` 增加日志驱动修复，把作者自己写的那组选项用
   `\PassOptionsToPackage{table,dvipsnames}{xcolor}` 提前到 `\documentclass` 之前。
2. **arXiv 路径丢掉自定义系统提示词、术语表、占位符规则**。
   该路径直接调 `translator.translate()`，BabelDOC 的 `do_translate` 用的是写死的
   极简提示词（"You are a professional,authentic machine translation engine."），
   配置档里的 `custom_system_prompt` 与术语表只在 BabelDOC 自己的 PDF 流水线
   （`il_translator_llm_only._build_llm_prompt`）里生效。修复：
   `babeldoc_runner.apply_arxiv_prompts` 在实例上覆写 `prompt()`，system 消息 =
   自定义规范 + 结构规则 + 术语对照表；并发/提示词变化都刷新缓存影响参数。
3. **串行翻译慢到不可用**（0.75%/分钟 → 一篇 67KB 的 main.tex 要 1.5~2 小时）。
   修复：`_map_parallel` 有界并发（默认 4，`YIYUE_TRANSLATE_WORKERS` 可调），
   进度回调只在主线程发、取消立即生效、统计局部收集后合并；实测 2.8%/分钟（÷3.7）。
   途中还修掉自己引入的两个问题：每块新建线程池把解释器逼到
   `Windows fatal exception: 0x8007000E`（改为共享看门线程池）、
   以及"等于没翻译"误判（见下）。
4. **两处误判让报告失真**（都是"验证器/启发式"的问题，不是翻译本身）：
   - `_looks_untranslated` 把 `{HTML}{1B2A32}` 这类**纯宏/颜色块**判成"没翻译"
     （模型原样返回本来是正确结果）→ 白重试两次后整块回退。改为只认**成句英文**
     （连续 ≥4 个字母词的串），这类块不再报警。
   - PDF 层"章节标题计数"被中文断行与表格编号行干扰，把结构完好的论文判成
     "可能有整节内容丢失"。新增**源码层 `\section` 命令数**作为硬判据
     （`count_section_cmds`，已剔除 `\sectionname` 这类宏名与注释），
     PDF 计数降级为提示。

## 顺带修的翻译鲁棒性（由本任务的真实失败驱动）

- **失败块拆半重试**：整块两次不合格时按段落边界劈成两半各试一次。本任务有一段
  正文（"The decisive test holds the invariant fixed…"）两次都因占位符校验失败而
  回退英文，拆开后成功翻译（`chunks_split_recovered=1`，成品里已是中文）。
- **失败原因可诊断**：`chunks_failed_detail` 记录"为什么失败 + 片段"，
  `chunks_failed_english_words` 记录涉及的英文词数；验证器据此区分
  "真丢正文"（≥20 词 → 需人工复核）与"纯命令/结构块被回退"（→ 提示）。
